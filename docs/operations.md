## §1. 自動運用方針（最優先制約）

このプロジェクトの存続条件は**人手の最小化**である。

### §1.1 必須原則

- **同期処理の禁止**: HTTP ハンドラは即返却。重い処理は必ずキュー経由
- **手動運用ゼロ**: 通常運用で管理画面を開かないと回らない設計を禁ずる
- **通知は異常時のみ**: 正常完了は顧客への通知のみ。operator には Sentry / Slack
  で **エラー・コスト超過・SLA 違反** のみ届ける
- **マージは顧客の手で**: 自動マージは絶対にしない
- **観測可能性**: 全 job に traceId、構造化ログ、所要時間・トークン使用量を記録

### §1.2 自動化のレベル定義

| レベル | 内容 | 本プロジェクトの目標 |
|---|---|---|
| L0 | 全工程手動 | — |
| L1 | 一部自動 | — |
| L2 | 主要工程自動、手動介入を例外として扱う | **最低水準** |
| L3 | 例外も含めほぼ自動、人間は監督のみ | **目指す水準** |
| L4 | 完全自動、人間は撤退可能 | 過剰目標、目指さない |

L4 は信用リスク・規制リスクが大きいため目指さない。

### §1.3 月次運用サイクル

operator が月 1 回行う固定タスク（30 分以下を目標）:

1. 当月の収益・API コスト・粗利を確認
2. 連続失敗・サポート問い合わせのトレンドを確認
3. Anthropic / GitHub / Stripe / Cloudflare の規約・料金変更を確認
4. キーローテーションのスケジュール確認
5. 必要なら本書を更新

## §2. コスト制約と最適化

API コスト > 顧客課金 になると即赤字化する。**例外なく**以下を守る。

### §2.1 1 ジョブあたりの上限（暫定、Phase 1 完了時に再評価）

| プラン | API コスト上限 |
|---|---|
| Small  | $20 |
| Medium | $50 |
| Large  | $120 |

超過時は job を中断し、`cost_exceeded` 状態へ遷移、Sentry 通知、自動返金。

### §2.2 必須最適化

- **prompt caching** を全 agent 呼び出しで有効化（`docs/agent.md` §3.2）
- 大きなコンテキスト（リポジトリツリー、共通 system prompt）は cache 化
- ファイル単位処理ではファイル内容のみ可変、それ以外は cache hit を狙う
- **可能な限り codemod で機械変換**し、agent に渡すコンテキストを縮小
- 構造化分類・要約は Haiku、コード生成は Sonnet、難解な意味解析のみ Opus
- agent からの出力は構造化（JSON）に寄せ、無駄な自然言語を削る

### §2.3 計測

- 各 job のトークン使用量・コストを `jobs` テーブルに記録
- Anthropic Usage API（または等価のレポート機能）を 1 時間毎に取得し、当月累計を監視
- 当月累計が想定の 1.5 倍を超えたら全新規 job 受付を停止し、operator に通知

### §2.4 受付制約

- 2000 ファイル超は Enterprise 個別見積（自動受付しない）
- monorepo は受付拒否（Phase 5 以降の対応）。検出ロジックは
  `packages/agent/src/sizing.ts` に同梱

### §2.5 コスト可視化

- ダッシュボードに当月の累計コスト・コスト/job 中央値・粗利を表示
- 週次で Slack に要約を投稿（自動）

## §3. 観測性とインシデント対応

### §3.1 観測の三本柱

- **メトリクス**: jobs テーブルの集計（完了率、平均コスト、平均所要時間）
- **ログ**: 構造化ログ（JSON）、traceId で job をまたいで追跡可能
- **トレース**: 各 job の段階遷移を job_events で復元可能

### §3.2 アラート

operator に通知すべきイベント:

- API コスト累計が想定の 1.5 倍を超過
- 連続 3 件の `failed_ci`
- Anthropic / GitHub / Stripe の認証エラー
- Fly.io Machine の起動失敗
- DB 接続エラー
- セキュリティ警告（不審な webhook、想定外の repo アクセス試行）

### §3.3 インシデントランブック

重大事象別の初動手順。詳細は別途 ranbook ファイルで管理してもよい。

| 事象 | 初動 |
|---|---|
| API コスト急騰 | 新規受付停止、原因調査、必要なら job 上限を一時下げる |
| 顧客 repo の誤操作 | job 即停止、影響範囲調査、24h 以内に顧客連絡 |
| Anthropic 障害 | 受付停止、status page 表示、自動リトライは 1 時間後 |
| GitHub 障害 | 同上 |
| Stripe 障害 | 同上、課金受付停止 |
| データ漏洩疑義 | キーを即時ローテート、影響範囲特定、関係顧客に開示 |

### §3.4 バックアップとリストア

- D1 は日次バックアップを R2 に保存（Cloudflare のスケジューリング機能を利用）
- 保持期間: 30 日
- 復元手順:
  1. 該当バックアップを R2 からダウンロード
  2. 新しい D1 データベースに復元
  3. アプリの DSN を切り替え
- 復元手順は四半期に 1 回実演する（机上訓練でも可）

## §4. 顧客対応・サポート方針

### §4.1 サポート窓口

- 受付: 専用メールアドレス（Resend で受信転送）
- SLA: 営業日 1 日以内に一次返信
- 自動 FAQ: Landing page でカバー（ヘビーな手作業を避ける）

### §4.2 想定問い合わせとテンプレート

`docs/templates/support/` に返信テンプレートを置く（Phase 4 で追加）。最低限:

- 「移行が CI green にならない」: 失敗内容を確認、再実行 or 返金の判断
- 「特定パターンの未対応」: 該当パターンの仕様確認、Phase 計画を参照
- 「返金請求」: ポリシーに沿って即時処理
- 「データの取り扱いについて」: `docs/security.md` を要約して回答

### §4.3 やらない対応

- 個別カスタマイズ要望（公平性のため、機能要望は次回バージョンで）
- ライブ通話・スクリーン共有でのデバッグ（時間コストが高すぎる）

## §5. やらないこと（Phase 4 完了まで）

誘惑があっても以下は実装しない。

- 複数フレームワーク対応（Next.js 専念）
- リアルタイムログのストリーミング表示
- Slack / Discord 連携（顧客向け）
- 自社 CI の構築（GitHub Actions に依存）
- 自動マージ
- セルフホスト版の提供
- 多言語 UI（英語のみ）
- 無料プラン・無料トライアル
- 招待制ベータ以外のチーム機能
- 部分返金
- 月額サブスクリプション
- monorepo 対応

これらの要望が来ても、**Phase 5 候補としてメモするのみ**で実装着手しない。
